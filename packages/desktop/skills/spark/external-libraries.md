# Integrated external libraries

## Versioned patch registry

Spark keeps exact tested versions in `patches/registry.json`, including redirect-only adapters and the minimum Spark version for each patch. A version entry marked `"verified": true` has no patch: Spark tested that version as is, so it counts as supported and native preparation applies nothing to it. Old versions and their patch files are retained. Run `bun scripts/patch-registry.ts` after adding a version; validation rejects missing files, changed hashes, ranges and unknown metadata. Preserve an existing patch file when adding a newer recipe; give the new recipe a distinct file and `minSpark` entry.

Install, `spark prebuild`, `spark dev` and `spark build` check installed libraries before native work. Spark reads the latest registry and patches from `LegendApp/legend-spark` main over HTTPS, pins all files to one commit SHA, and caches that set by SHA. If the fetch fails, it prints a one-line notice and uses the patches bundled with the installed SDK. Build receipts record `runtime.patchSourceSHA` as that commit or `bundled`.

Spark selects the newest patch for the exact installed library version whose `minSpark` supports the installed Spark. If a newer recipe needs a newer Spark, it offers `spark upgrade`; declining keeps the compatible recipe. If no compatible patch or verified version exists, a terminal lists the supported versions with the newest compatible one as the default. Accepting updates `package.json` and reinstalls; declining stops. CI and piped commands fail with an exact install command. Shared `node_modules` installations prompt and repair at their shared root.

Use `"spark": { "patches": { "<library>": false } }` in `package.json` to skip a library's check and Spark patch. A shared-root opt-out applies to its apps. `spark doctor` reports the same version findings with a `Fix:` line without prompts, migrations or filesystem writes. App patches still layer after Spark's selected recipe. SDK-owned native archives retain their provenance checks; use the matching SDK archive overrides when installing them.

No new Expo-owned packages are added to this registry. Existing Expo patches and the existing Clipboard/Document Picker redirects remain supported.

## Optional backend dependencies

Apps using `/markdown`, `/html`, `/webview`, or `/sqlite` must install the matching optional peer: `react-native-enriched-markdown@1.1.1`, `react-native-enriched-html@1.1.1`, `react-native-webview@17.1.0`, or `@op-engineering/op-sqlite@18.2.1`, and keep the SDK's overrides for WebView and SQLite (see [UPGRADING.md](UPGRADING.md)). `spark doctor` reports missing declarations. Universal apps targeting Windows exclude `react-native-enriched-html` and `react-native-enriched-markdown` in `expoByPlatform.windows.autolinking.exclude` in `desktop.config.json`; they have no Windows implementation. Spark applies the Enriched Markdown/HTML compatibility patches automatically; no package-manager patch declaration is needed.

## Windows

Windows supplies an adapter for `react-native-nitro-modules` 0.37.0 (the Nitro C++ runtime through RNW JSI). A Nitro library with only Swift/Kotlin implementations still needs its own Windows implementation. Windows external-library integrations are implemented in source but not yet verified on x64 and ARM64 hardware; WebView follows upstream Windows prop coverage.
